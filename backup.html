1. Purpose and Scope

This policy defines the strategy and procedures for data backup and disaster recovery to ensure the continuity of Vadom Data Consulting’s critical services. This policy covers all production infrastructure hosted on Amazon Web Services (AWS), including Compute (EC2), Databases (RDS), and Storage (S3/EBS).

2. Infrastructure Overview

Our production environment is hosted in a Virtual Private Cloud (VPC) on AWS, utilizing a high-availability architecture managed by certified AWS Partners.

  • Primary Cloud Provider: Amazon Web Services (AWS).
  • Database Engine: Amazon RDS for PostgreSQL (Managed Relational Database Service).
  • Storage Systems: Amazon S3 (Object Storage) and Amazon EBS (Block Storage).

3. Backup Strategy

Vadom Data employs a comprehensive backup strategy utilizing AWS Backup and native RDS snapshot capabilities to ensure data durability and recoverability.

3.1. Database Backups (RDS PostgreSQL)

  • Automated Snapshots: Full database snapshots are taken automatically on a daily basis during the defined maintenance window.
  • Transaction Logs: Transaction logs are backed up every 5 minutes to allow for Point-in-Time Recovery (PITR).
  • Redundancy: To ensure resilience against zonal failures, database exports are stored three (3) times per day in a different Availability Zone (Multi-AZ architecture) using Amazon EFS/S3 integration.
  • Retention: Automated backups are retained for a minimum of 30 days.

3.2. Server & File System Backups

  • EC2 Instances: Machine images (AMIs) and EBS volume snapshots are created daily via AWS Backup policies.
  • Static Files (S3): S3 buckets maintain versioning to recover from accidental deletions or overwrites. AWS S3 provides 99.999999999% data durability.

4. Security of Backups

  • Encryption: All backup data, snapshots, and transaction logs are encrypted at rest using AES-256 encryption standards managed via AWS KMS (Key Management Service).
  • Access Control: Access to backup repositories is strictly restricted to authorized Cloud Administrators and DevOps personnel via IAM (Identity and Access Management) roles. Backup deletion requires Multi-Factor Authentication (MFA).

5. Disaster Recovery (DR) Plan

In the event of a catastrophic failure (e.g., data center outage, cyberattack, or massive data corruption), the following recovery objectives are established:

  • Recovery Point Objective (RPO): Maximum 5 minutes for Database transactions (via PITR) and 24 hours for full system snapshots.
  • Recovery Time Objective (RTO): Critical services shall be restored within 4 to 8 hours depending on the severity of the incident.

5.1. Restoration Procedure

  • Incident Declaration: The Critical Incident Response Team identifies the outage.
  • Assessment: The team determines if a full region/zone failover or a simple data restoration is required.
  • Execution: New instances are provisioned from the latest healthy AMI/Snapshot. Databases are restored to a new RDS instance using the Point-in-Time recovery feature.
  • Verification: Integrity checks are performed before switching DNS traffic to the recovered environment.

6. Testing and Maintenance

The integrity of backups is verified automatically by AWS. Full restoration drills are conducted quarterly to ensure the RTO/RPO targets are met and to validate the effectiveness of the disaster recovery procedures.
