1. Purpose and Scope

The purpose of this policy is to define the minimum cryptographic standards required to protect the confidentiality and integrity of Vadom Data Consulting’s information assets and its clients' data. This policy applies to all systems, databases, networks, and applications managed by Vadom Data, specifically those processing Restricted or Confidential information.

2. General Principles

  • Default Encryption: All sensitive data (PII, Financial, Authentication Secrets) must be encrypted both at rest and in transit to prevent unauthorized access.
  • Strong Algorithms: Only industry-standard, strong cryptographic algorithms (e.g., AES, RSA, SHA-2) are permitted. Proprietary or outdated/weak algorithms (e.g., DES, MD5, SHA-1) are strictly prohibited for security functions.
  • Key Management: Cryptographic keys must be managed securely throughout their lifecycle, ensuring separation of duties between key custodians and data owners where possible.

3. Encryption Standards – Data in Transit

All data transmitted over public networks (Internet) or internal wireless networks must be encrypted using secure protocols to prevent interception or tampering.

  • Web Traffic (HTTP): All web applications must enforce HTTPS.
  • Protocol Version: TLS 1.2 or TLS 1.3 is mandatory. Support for SSLv2, SSLv3, TLS 1.0, and TLS 1.1 must be disabled on all servers.
  • Certificates: Only valid X.509 certificates issued by a trusted Public Certificate Authority (CA) are accepted. Self-signed certificates are not permitted in production.
  • Remote Access: VPN connections and administrative access (SSH/RDP) must be tunneled through secure encrypted channels.
  • File Transfer: Transfers of sensitive files must occur via SFTP (SSH File Transfer Protocol) or HTTPS, never via plain FTP.

4. Encryption Standards – Data at Rest

Sensitive data stored in databases, file systems, or backups must be rendered unreadable to unauthorized users.

  • Databases: Must use Advanced Encryption Standard (AES) with a key length of 256 bits (AES-256). Implementation via Transparent Data Encryption (TDE) or column-level encryption for critical fields (e.g., Tax IDs, Bank Accounts).
  • File Storage (Cloud/On-Premise): Files and documents (PDFs, Images) containing sensitive information must be encrypted using Server-Side Encryption (SSE) with AES-256.
  • Backups: All backup media (virtual tapes, snapshots, buckets) must be encrypted before being stored offsite.

5. Authentication & Secrets Management

  • Passwords: User passwords must never be stored in plain text.
  • Hashing: Passwords must be salted and hashed using a slow, intensive algorithm such as PBKDF2 (with HMAC-SHA256), bcrypt, or Argon2.
  • Salting: A unique, random salt of at least 16 bytes must be generated for each user credential.
  • API Keys & Secrets: Application secrets must not be hardcoded in source code. They must be injected via environment variables or retrieved from a secure Vault / Secrets Manager.

6. Key Management Lifecycle

  • Generation: Keys must be generated using a cryptographically secure pseudo-random number generator (CSPRNG).
  • Rotation: Encryption keys for production data should be rotated automatically at least once every 365 days, or immediately upon suspicion of compromise.
  • Storage: Keys must be stored separately from the encrypted data (e.g., using a dedicated Key Management Service - KMS or Hardware Security Module - HSM).

7. Policy Compliance

Violations of this policy may result in disciplinary action. The Security Team will perform annual audits and vulnerability assessments to verify compliance with these cryptographic standards.
